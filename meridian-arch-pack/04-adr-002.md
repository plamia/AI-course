# ADR-002: Implement Event-Driven Inventory Reconciliation via Kafka and Outbox Pattern

## Status
Accepted

## Owner
Architecture Team

## Source and Freshness
- **Source:** Meridian Case A brief; SAP ECC 15–30 min sync constraint; phantom-stock mitigation requirements.
- **Last Reviewed:** 2026-09-26
- **Status:** Accepted

## Review Trigger
Re-evaluate when SAP S/4HANA migration occurs, event throughput exceeds cluster capacity, or real-time SAP event streaming becomes available.

## Context
SAP ECC serves as the inventory system of record with 15–30 minute batch sync windows. Direct synchronous calls from storefronts and POS terminals cause latency spikes and fail to resolve the ~7% phantom-stock cancellation problem during high-concurrency retail events.

## Decision
We will implement an event-driven architecture using **Apache Kafka** paired with the **Outbox Pattern** for reliable local state changes and asynchronous inventory reconciliation with SAP ECC.

## Alternatives Considered
1. **Direct Synchronous SAP OData Calls:** Rejected because SAP ECC cannot handle real-time synchronous queries from 1,400 stores without violating the p95 $\le 1.5\text{s}$ latency budget and risking catastrophic SAP failure during traffic spikes.
2. **Distributed 2-Phase Commit (2PC):** Rejected because distributed locking across regional stores and SAP ECC introduces severe performance bottlenecks and vulnerability to network partitions.

## Consequences
- **Positive:** Sub-second availability checks ($\le 200\text{ms}$); reliable message delivery via Outbox; SAP ECC protected from direct traffic spikes.
- **Negative:** Introduces eventual consistency challenges requiring compensating Sagas for stock reconciliation failures.

## Agent-Readable Summary
All cross-service ordering and inventory state changes MUST use the Outbox pattern and publish events to Kafka. Do not introduce direct synchronous calls between Order, Cart, and Inventory services; all stock availability checks must query the local Redis read-cache.
